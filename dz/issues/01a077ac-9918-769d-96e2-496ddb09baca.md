JitFunctionData::kRecompileDeclineThreshold (64) is a compile-time
constant; the only runtime knob today is -Xjit-max-recompiles. Add a
runtime flag so the trigger's eagerness can be tuned and experimented
with, without rebuilding.

Shape: mirror the -Xjit-max-recompiles plumbing exactly — RuntimeFlags
opt (-Xjit-recompile-threshold, default 64), RuntimeConfig field,
tools/hermes/hermes.cpp builder chain, tools/test-runner/Executor.cpp
(do not repeat the omission the final review caught there), Runtime.cpp
application, JITContext member + setter on x86-64/arm64/stub. The
constant becomes the default value; the trigger tail in _jit_put_by_id
reads the JITContext value (via the JitFunctionData? simplest: snapshot
the threshold into JitFunctionData at first ensureJitData, next to the
budget, so the helper tail keeps touching a single cache line).

Lit tests pin threshold-crossing behavior at 64 (recompile-byid-warm,
recompile-phased-warming, recompile-mid-recursion count on ~64+
declines); they keep working under the default, and a small new test
should pin that a non-default value (e.g. =8) triggers earlier.

Wanted soon, per discussion 2026-09-06.
