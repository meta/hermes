High-level strategy, of which the two folded PutByVal perf issues are
both instances. Per instruction site there are three kinds of emitted
code: fast paths, slow paths that record, and plain slow paths. We
want to learn whether a site has a particular fast path, a combination
of fast paths, or only a slow path, and emit the best code based on
that knowledge. The current implementation gets the learning right and
the TERMINATION wrong: recording never ends.

The state space, made explicit: per site per version, the emitted code
is (a subset of fast paths) + (a fallback flavor) + (optional
instrumentation on a fast path). Recorded knowledge today is monotone
-- jsArraySeen and otherSeen are sticky, taKind only moves
none -> mono -> poisoned -- so the knowledge states form a finite
lattice and every site's history is a bounded monotone climb. A state
is TERMINAL when no observation reachable from it could change what we
would emit.

Two invariants the current implementation violates:

I1. Every site must reach a terminal state whose code records
    nothing. Violated: the fallback at every version is the recording
    helper; nothing ever selects the plain _sh_ljs call back. Cost:
    Float16 fill 183->259 ms (0.71x), and ~5-10% on every
    permanently-declining shape (plain-object stores, non-number
    values, string keys).

I2. Instrumentation may live only on paths that generate events,
    because a fast path produces no event stream to carry a
    transition out of the instrumented state. Violated: the sticky
    flag on the fast path makes fast+recording an absorbing state for
    quiet pure-JSArray sites. Cost: dense-array control 47->49 ms
    (0.96x), permanent.

The transition rule that resolves the demotion circularity: a
threshold crossing that changes no knowledge and enables no
improvement is ITSELF the trigger to emit terminal code. Demotion is
not "progress" and must not be gated on it; the lattice is finite, so
demotions are bounded per site and need no improvement budget.

Instances, restated in this frame:
- Keep a prior JSArray tier unless evidence is otherSeen-only (the
  fe68 proposal) is I2 applied: it deletes the only fast-path
  instrumentation we have.
- Demote hopeless sites to the plain helper (the fe7e proposal) is I1
  applied, with the trigger above replacing the missing "progress".
- A TA-specialized site's recording fallback is LEGITIMATE: its
  declines still teach (poison, jsArraySeen), and their volume is low
  -- recording tax only matters where the recording path is dominant,
  which is exactly the non-terminal-but-absorbing states I1/I2 name.
- The Float16/F16C tier is orthogonal capability work: it moves a
  shape from "no fast path exists" to "fast path exists", it does not
  fix termination.

Open question (deliberately left open): lattice or graph. Monotone
knowledge converges cheaply but a phase change can strand a site in a
stale terminal state; re-learning (epochs, decay) turns the lattice
into a graph and needs explicit anti-oscillation. Today's answer is
lattice; revisit only with evidence of real phase-change workloads.

Secondary question, mostly mooted by termination: cheapening the
recording slow path (fast exits, slimmer classification) only shrinks
the cost of TRANSIENT states; if every site terminates promptly, the
recording path's cost stops mattering at steady state.

Measurements (per-kind fill benchmark, base -> head, -Xjit=force):
    Int32Array   HV64 153->50 (3.06x)   HV32 169->49 (3.45x)
    Uint8Array   HV64 152->49 (3.10x)   HV32 167->48 (3.48x)
    Float64Array HV64 146->50 (2.92x)   HV32 163->50 (3.26x)
    Float16Array HV64 183->259 (0.71x)  HV32 195->272 (0.72x)
    poisoned     HV64 159->141 (1.13x)  HV32 166->143 (1.16x)
    dense Array  HV64 47->49 (0.96x)    HV32 52->53 (0.98x)

    Discussion refinement: demotion should NOT be a recompile. Recompiling
    just to tell the slow path to stop recording is too heavy. Instead,
    make the helper target per-site mutable state:

    - The site record gains a helper-pointer slot, initialized to
      _jit_put_by_val_{loose,strict}. The emitter embeds the SLOT address
      (as it did for the sticky flag) and emits
      `movabs r11, &site.helper; call qword ptr [r11]` -- same two
      instructions as today's direct call; the only added cost anywhere
      is one dereference per helper call, on a path that is slow by
      definition.
    - When a threshold crossing concludes "no knowledge changed, nothing
      can improve", the helper stores _sh_ljs_put_by_val_*_rjs into the
      slot. That IS the demotion: from the next store on, the site calls
      the original pre-feature helper directly -- not a recording helper
      with an early-out. Terminal cost = plain helper + one load.
    - The 6-arg/4-arg signature mismatch absorbs itself: the call site
      sets up six args, a four-arg callee ignores r8/r9 under SysV. One
      call sequence serves both targets.
    - Heap-resident slot, single-threaded runtime: no code patching, no
      W^X question, no atomicity ceremony. Per-version isolation for
      free (slot lives in the version record, like the decline counter).
    - Monotone by construction: nothing ever flips the pointer back, and
      once flipped no observations are being made anyway -- mechanism and
      lattice semantics agree.

    The flag-check alternative (terminal bit tested at helper entry,
    tail-call the plain helper) is simpler but permanently keeps the call
    hop and the test; if the call sequence is touched at all, the pointer
    wins.

    Residuals: (1) only a recompile can also delete a hopeless site's
    dead inline guards (~6 cycles/store for a vestigial JSArray tier at a
    plain-object site) -- let that ride along whenever a real
    improvement-recompile happens for another site in the function; it
    stops being a reason to recompile on its own. (2) This fixes I1 only;
    the sticky flag lives on the fast path, where there is no call to
    indirect through -- I2 still has no better answer than not
    instrumenting fast paths (the keep-the-prior-array-tier rule).

    Architectural note: a per-site patchable call target is the same move
    as an inline cache's dispatch, and generalizes to the ById recording
    helpers when their time comes.
- 2026-09-09T02:20:17.537Z  Tzvetan Mikov <tmikov@gmail.com>  comment
    Discussion resolution: the "hits are invisible" asymmetry -- and with
    it the monotone-emission (keep-the-prior-tier) rule -- is an artifact
    of the ByVal fast path being STATELESS. The tier re-derives everything
    from the value each time (kind byte, flags, bounds -- immediate
    compares baked into code), so a hit touches no state and leaves no
    trace. The ById tiers sit on the other side of the line: their guard
    references a per-site cache, and the cache is DATA -- written by the
    slow path, readable at compile time, clearable at will. Guards in code
    give the fastest hit and write-only emission decisions; guards in data
    cost a load per hit and give a full observation channel.

    Consequences of an HC-keyed per-site cache for ByVal:

    1. Observability for free, in the form we already exploit: "is array
       traffic present" becomes "does the site's cache hold an array HC"
       -- the warm/cold proxy considerRecompile already reads for ById.
       No sticky flag, no monotone-keep rule; the JitByValSiteRecord
       taxonomy (jsArraySeen/taKind/otherSeen) collapses into cache-entry
       inspection, and the existing cold-site/warm-scan policy applies to
       ByVal verbatim. One policy, two consumers.

    2. Removal becomes observable AND cheap -- the thing monotonicity
       could not give: clear the cache to probe; if the tier's traffic
       exists it declines once and re-warms, no recompile, regression
       window of a few helper calls. In lattice terms: code-guards force
       adaptation through recompiles (expensive edges, so monotone
       convergence is right); data-guards make most edges a store, and
       the graph answer becomes affordable. Lattice-vs-graph is the same
       question as guards-in-code vs guards-in-data.

    3. The recording-cost question mostly evaporates: our recording is
       expensive because it is bespoke (call hop, deque lookup,
       classification switch). ById's slow path writes its cache on
       every miss and it has never been a tax -- a store to a slot whose
       address is baked in. HC-write recording is ~2 instructions; the
       pointer-flip demotion drops from must-have to nice-to-have.

    Likely landing spot (hybrid): KEEP the stateless value-checked tier
    as the emitted fast path (fastest thing we can emit; note even the
    ById tiers bake the clazz ID as an immediate and use recompilation to
    refresh it -- the cache there is the observation channel, not the
    guard), and make the slow path's recording an HC write into a
    cache-shaped slot. ById-grade observability and recording cost,
    stateless-tier speed.

    Load-bearing dependency: whether the HC can carry what ByVal needs
    (array-ness, typed-array element kind) efficiently -- the parallel
    HC-tracking work. If every interesting shape distinction has an
    HC-visible identity, the unification also covers what the current
    records cannot see at all (sealed/frozen transitions, fast-index
    loss, which ARE HC/flag transitions), and Get/PutByVal become
    "property access with a computed key" all the way down to the
    feedback machinery.

    the recording helper's slot is per-site mutable state; a demotion pass
    in considerRecompile flips a hopeless site's slot to the matching
    plain _sh_ljs_put_by_val_*_rjs helper after 3 stable threshold
    crossings (4 from cold, since the first crossing is always a
    "changed" crossing), and retirement demotes every remaining recording
    site in the retired body unconditionally. NumByValDemotions and
    end-to-end tests (recompile-taval-demote.js, -demote-delay.js,
    -demote-carried.js) pin it.

    sticky jsArraySeen fast-path flag is deleted outright. The JSArray
    tier is now a static, uninstrumented prior emitted at every eligible
    site in every version (monotone emission); only the typed-array tier
