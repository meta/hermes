A comparison yields a boolean, and coercing it back to a number emits
`AsInt32Inst` (`ToInt32`) on that boolean. The commit "[SH] JIT:
x86-64: inline ToInt32/ToUint32 of a statically known bool" made the
x86-64 JIT handle that inline when the input FR is statically known to
hold a bool, which is worth 2.03-2.56x on
`benchmarks/jit-benches/bool-to-int32.js` and 1.16-1.18x on a Wasm Game
of Life kernel.

That fix is incomplete by construction: bool-ness is tracked as a
**per-basic-block local** FR type. A loop-invariant comparison is
hoisted out of the loop body, so the `ToInt32` left in the loop no
longer sees a statically known bool and the fast path cannot apply.
Measured while writing the benchmark:

- `((i & 7) === 3) | 0` -- comparison in the loop body -- takes the
  fast path, no slow path emitted.
- `(a === b) | 0` with loop-invariant `a`/`b` -- comparison hoisted --
  still emits and takes the out-of-line `_sh_ljs_to_int32_rjs`.

Folding at the IR level removes the problem at its source rather than
making the conversion cheaper: an `AsInt32Inst` whose operand is a
comparison could become one operation that produces the number 0 or 1
directly. No boolean is materialized, there is no `ToInt32` left to
speed up, and the result does not depend on basic-block-local type
information, so it holds wherever the compare ends up.

`reduceAsInt32` in `lib/Optimizer/Scalar/InstSimplify.cpp` currently
folds only a literal operand:

```cpp
Value *reduceAsInt32(AsInt32Inst *asInt32) {
  auto *op = asInt32->getSingleOperand();
  if (auto *lit = llvh::dyn_cast<Literal>(op)) {
    if (auto *result = evalToInt32(builder_, lit))
      return result;
  }
  return asInt32;
}
```

Shapes to cover: `FCompareInst` (what WasmIRGen emits -- see
`WasmIRGen::onI32Eq`/`onI32Ne`/`onI32LtS`/... on the wasm branch, each
of which is `createFCompareInst` followed by `createAsInt32Inst`), and
the generic comparison instructions whose result type is boolean.
`AsUint32Inst` wants the same treatment: on a 0/1 value the signed and
unsigned conversions agree.

Implementation needs somewhere for the folded form to live -- either a
new IR instruction (compare producing a number) plus a bytecode, or a
reuse of an existing one. The x86-64 JIT could emit it branchlessly as
`ucomisd` + `setcc` + `movzx` + `cvtsi2sd`.

Worth more than the Wasm case alone: plain JS `(a === b) | 0` and
`(a < b) >>> 0` have the identical shape, and the Wasm lowering emits
one per `i32.eq`/`ne`/`lt`/`gt`/`le`/`ge`.

Found while profiling a Wasm Game of Life kernel, where ToInt32 on
booleans was the entire remaining runtime overhead: a counter in the
non-number branch of `_sh_ljs_to_int32_rjs` recorded 60M calls in a
2.3 s run, 100% of them bools.

    Two constraints on the fold, from an external review of the JIT-side
    fast path (which this issue is the follow-up to):

    1. "The boolean never materializes" only holds when the comparison's
       sole consumer is the AsInt32/AsUint32. A comparison feeding both a
       conversion and a branch (or any other boolean consumer) still has to
       produce a boolean, so the fold has to be conditional on the use set
       rather than unconditional.

    2. The fold must preserve where and how often the comparison is
       evaluated. The generic comparison instructions can perform coercions
       with observable effects, so sinking or duplicating a comparison into
       its conversion sites would be unsound. A fused form has to sit where
       the comparison already was, and appear exactly once per original
       comparison.

    Also worth noting the JIT-side guard is narrower than "a comparison
    result": isFRKnownBool requires locally established bool-ness, and
    newBasicBlock resets localType to globalType while `enter` only ever
    assigns Number or UnknownNonPtr globally -- never Bool. So the fast
    path is confined to a single basic block by construction, which is
    what makes an IR-level fold the durable fix rather than a wider FRType
    propagation.
