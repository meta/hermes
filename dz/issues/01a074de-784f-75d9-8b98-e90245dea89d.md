From the external review REVIEW-jit-recompilation.md (2026-09-06),
architectural finding; observed live under a debugger (old-body caller,
new-body target, correct result).

Compiler::compileCodeBlock() rewrites the RuntimeModule's SHARED
string-switch tables (StringSwitchDenseMap entries' jitCodeTarget) to
point into the body it just produced. After a recompile, an OLD
activation's next _jit_string_switch_imm_table_lookup returns an address
inside the NEW body and the old frame branches into it mid-function.
This contradicts the recompilation design's isolation claim ("old
activations finish on the old body") and is correct today only through
implicit invariants: frame layout and global-register assignment derive
deterministically from unchanged bytecode, and the landing point is a
basic-block boundary where temporaries are synced and local types reset.

Any future change to per-version register allocation, frame layout, or
retired-code reclamation (see the reclamation issue) silently breaks
this. The design doc's claim is amended to note the exception; this
issue tracks removing it.

Fix direction: make the shared table version-independent and the code
addresses version-local. E.g. the table maps string -> case index; the
lookup helper returns the index (or -1 for default); each compiled body
emits its own case->address jump table in RO data and performs the
indexed jump locally. Both backends' emitters change in mirrored form.
Regression: an activation that recompiles mid-switch-loop and continues
switching in the old body (differential vs interpreter), plus a pin that
the shared table no longer stores code addresses.
