From the external review REVIEW-jit-recompilation.md (2026-09-06),
finding 2 (P2); reproduced on the current tip. Supersedes the deferred
"lazy-id exhaustion" minor from the recompilation branch reviews: the
cost is worse than one wasted recompile because it compounds with the
coarse progress check.

In the PutById emitter (lib/VM/JIT/x86-64/JitEmitter-property.cpp), the
cold-site count uses `!clazzID`, but initHCLazyIDMayAlloc() also returns
0 for a warm, non-null class when the lazy-ID space is exhausted (or
pinning OOMs). Such a site is counted cold although no recompile can
ever specialize it, and its warm cache satisfies the progress check, so
every threshold crossing spends budget on an identical body. Verified
with -Xjit-hc-id-limit=0 -Xjit-max-recompiles=3: versions 1-4 all
report one cold site, JIT memory 338->1554 bytes, no tier possible.

Fix direction: count a site cold only when cacheEntry->clazz is actually
null; a non-null class with failed ID allocation is permanently
unspecializable and must not advertise a warming opportunity. The
GetById side already tests the class directly and is unaffected.
Regression: the exhaustion reproducer must compile exactly once.
