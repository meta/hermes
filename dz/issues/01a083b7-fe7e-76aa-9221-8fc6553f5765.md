A site whose traffic is an unsupported typed-array kind (Uint8Clamped,
Float16, BigInt64/BigUint64) records as otherSeen. An otherSeen-only
site can never qualify as progress, so it never recompiles -- but
every store takes the recording helper: the extra call hop, the deque
site lookup, the kind classification, the shared decline counter, and
a full considerRecompile early-out every 64 stores, stacked on the
helper path it already paid at base. There is a circularity: the
natural fix (recompile once to a plain non-recording helper call)
needs a recompile, and the no-progress gate exists precisely to
prevent that recompile.

Measured (per-kind fill benchmark, base = pre-feature, head = with
feature, -Xjit=force):

    Float16Array fill  HV64 183->259 ms (0.71x)  HV32 195->272 (0.72x)

~3.8 ns/store of bookkeeping with zero possible payoff.

Options, in order of preference:

1. Implement the Float16 tier: F16C vcvtps2ph makes the conversion
   about as cheap as Float32's cvtsd2ss (guard on CPUID or gate the
   kind on F16C availability at JIT startup). Turns 0.71x into ~3x
   instead of merely back to ~1x. Does not help Uint8Clamped
   (round-half-even sequence, doable) or the BigInt kinds (value must
   be BigInt; ToNumber semantics do not apply -- likely permanent
   helper kinds).
2. A one-shot "demotion" recompile for hopeless sites (otherSeen-only
   after N crossings): re-emit the site as a direct
   _sh_ljs_put_by_val call, removing all bookkeeping. Spends budget
   to remove overhead; needs a progress-gate carve-out.
3. Early-out the recording when otherSeen is already set and no other
   field could change (cheapens classification only; the call hop
   and counter remain, so this recovers a fraction).

The same tax applies to any permanently-declining site regardless of
kind (e.g. a same-kind site that always stores non-numbers). Related:
the sticky-flag tax issue filed alongside this one; 01a0828c item on
the missing execution-proof counter, which would also measure this
overhead directly.

    Generalization: this is not an unsupported-kind problem. The fallback
    call at EVERY version is the recording helper -- tier selection decides
    which inline tiers precede it, but nothing ever selects the plain
    _sh_ljs helper back -- so every decline at every site in every version
    pays the recording delta (call hop, deque site lookup, classification,
    shared counter, a considerRecompile early-out each 64th crossing, ~12
    cycles). Permanently-declining traffic of any shape is slower than
    base: plain-object stores (o[k] = v stays in v1 forever, paying dead
    JSArray-tier guards + recording + the generic helper; even after an
    externally-triggered recompile drops the tier, ~6 saved guard cycles
    buy ~12 recording cycles), non-number values, string keys. The hit is
    proportional to the helper path's own cost: ~5-10% on the heavy
    generic-object path vs 42% on Float16, whose helper-side fast path is
    cheap.

    Additional option (cheaper than demotion, no trigger needed): a
    helper-side fast exit -- when the site's record is in a terminal state,
    skip classification and counting and forward directly, cutting the
    delta to a load-test-branch. The terminal-state condition needs care:
    an early-exit on bare otherSeen would blind a mixed object+Int32Array
    site to its specializable half; something like "otherSeen set, taKind
    poisoned-or-None, after N wrapped crossings" keeps late discovery
    possible while capping the tax.
