HiddenClass::findPropertyNoAlloc (lib/VM/HiddenClass.cpp:365-390) walks the transition chain when a class has no property map and, on the first class whose symbolID_ matches, returns {propertyFlags_, numProperties_ - 1} (:382-384). That is right for an addition transition but not for a flags transition: updateProperty (HiddenClass.cpp:608-665) creates a child whose symbolID_ is the changed property and whose numProperties_ is unchanged, so the property keeps its old slot.

Example: {x: 10, y: 20}, then make x non-writable. If the resulting class has no map (transitions steal maps, HiddenClass.cpp:549), the lookup reports x at slot 1 instead of 0. It also returns the internal flagsTransition bit, which map reconstruction clears (HiddenClass.cpp:1235).

Callers: JSObject::tryGetNamedNoAlloc (include/hermes/VM/JSObject.h:2122-2131), used for the name/constructor lookups at lib/VM/JSObject.cpp:2555-2712.

Found by Codex while reviewing doc/superpowers/specs/2026-10-24-jit-getbyid-chain-design.md, which avoids the function for this reason. Not reproduced yet.

    Reproduced and fixed. HiddenClassTest.FindPropertyNoAllocFlagsTransitionTest builds {a, b, c}, changes b's flags twice, then adds d and e so the flags-transition class and the class below it both lose their map. Before the fix, findPropertyNoAlloc reported b at slot 2 with flagsTransition set, from both classes. The fix: on a flags transition of the name, it keeps the newest flags (with flagsTransition cleared) and keeps walking until the class that added the property, or a map, supplies the slot.
