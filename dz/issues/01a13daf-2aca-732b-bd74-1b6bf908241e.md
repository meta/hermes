`byIdSiteCanProgress` (lib/VM/JIT/JitCompiler.cpp) counts any live,
un-emitted, emittable entry as progress, even one recorded by a single
decline. A shape that the body's generic read-cache tier then serves
inline never declines again, yet it still makes the next threshold
crossing spend recompile budget.

Repro (x86-64, `-fno-inline -Xjit -Xjit-emit-counters`):

```js
function get(o) { return o.x + (o.missing === undefined ? 0 : 1); }
var A = {x: 1}, B = {y: 2, x: 3};
var s = 0;
for (var i = 0; i < 200; ++i) s += get(A);          // warm compile on A
for (var i = 0; i < 2000; ++i) s += get(i & 1 ? A : B);
print(s);
```

`o.x` misses once on B, records it, and from then on the generic tier
serves B inline. The uncacheable `o.missing` read keeps declining and
supplies the threshold crossings, and the recorded B entry is what
turns one of them into a recompile. Measured at 270d72019:
NumRecompiles 1 (NumByIdDemotions 2). With A only: NumRecompiles 0.
Without the `o.missing` read: NumRecompiles 0.

This is a likely contributor to TypeScript's 334 recompiles at head vs
80 at base (spec 2026-10-14-jit-getbyid-polymorphic-design.md,
Delivered/Benchmarks), for a flat score.

Candidate fix: a saturating per-entry miss count, with progress
requiring >= 2 misses. That changes spec'd boundary behavior
(getbyid-poly-boundary.js pins a recompile after one miss), so it needs
a spec amendment first. Measure TypeScript's compile-time share before
choosing.
