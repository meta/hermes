Octane TypeScript: 74% of GetById slow-path calls under -Xjit have a string primitive receiver (22.2M calls, 49 sites). `charCodeAt` is 44% and `length` 27%, then `substring` and `indexOf`. About 13M of these are in the benchmark harness's checksum loop `Verify` (typescript.js:473-474: `s.length`, `s.charCodeAt(i)`); 7.1M are in the compiler's `Scanner.prototype.peekChar` (typescript.js:13262: `this.src.charCodeAt(this.pos)`).

Measured at e5c158faa (Release, -Xjit, from .hbc).

## Profile

Without -Xperf-prof, which by itself costs about 13% of the score (44,944 vs 51,393). DWARF call graphs; this AMD CPU has no LBR, and frame-pointer -g cannot walk the Release C++ frames.

| bucket | % of cycles |
|---|---|
| GetById helpers on string receivers | ~8.1 |
| ... String.prototype method lookup | ~5.1 |
| ... `length` plus dispatch | ~3.0 |
| `charCodeAt` call (stringPrototypeCharCodeAt 4.3 inclusive + its share of _jitCallImpl) | ~5.2 |
| object-receiver GetById misses, for contrast | ~3.3 |

## Current path

- Emitted code: `emitFastPath` jumps to the slow path when the receiver is not an object (x86 JitEmitter-property.cpp:941, arm64 :1037), so neither the poly chain nor the read-cache compare runs.
- `recordByIdObservation` returns early for non-objects (JitHandlers.cpp:584), so these sites record nothing and demote to a direct `_sh_ljs_get_by_id_rjs` call (JitCompiler.cpp:430-442).
- Helper chain: `_sh_ljs_get_by_id_rjs` -> `getByIdTransientWithReceiver_RJS` (StaticH.cpp:1258) -> `getPrimitivePrototype` -> `getNamedWithReceiver_RJS(stringPrototype, no cache)` -> `getNamedDescriptorUnsafe`, a hash probe. Four out-of-line calls per method lookup. The read property cache is never read or filled for primitive receivers, in the JIT, StaticH or the interpreter.
- `length` has one special case, `tryGetPrimitiveOwnPropertyById` (Interpreter-slowpaths.cpp:1563), which still costs two C++ calls per read.
- The call: JIT `callImpl` spills temps, a NativeFunction goes through `jitCallArray` -> `NativeFunction::_jitCallImpl`, and `stringPrototypeCharCodeAt` (String.cpp:719) does LocalsRAII, an out-of-line `toString_RJS`, `toIntegerOrInfinity` and `createStringView`. No known-callee or inlined-builtin mechanism exists; CallBuiltin / -fstatic-builtins cover only static methods and lower to `_jit_call_builtin`. The compiler has no type information at these sites (plain GetByIdShort + Call2).

## Facts for a design

- `length`: `StringPrimitive::lengthAndFlags_` (StringPrimitive.h:40, mask 0x3fffffff) is in the base class, uniform for every kind. `RuntimeOffsets::stringPrimitiveLengthAndFlags` and `emit_stringprim_get_length_and_flags` already exist (used by the strict-equality fast paths). The string tag check is the only guard: Lowering.cpp:246 guarantees a GetById name is never an array index. JIT registers hold the same 64-bit HermesValue in every heap HV mode.
- Characters: no ropes (`isFlat()` always true). ASCII vs UTF-16 is the kind's parity bit. Dynamic and DynamicUniqued kinds store characters after the header at a constant offset; External kinds go through a `std::basic_string*` (library-dependent layout); Buffered kinds point at an External. The scanner's source is an External ASCII string (IdentifierTable.cpp:261), so inline char reads need a non-allocating helper for External/Buffered.
- Methods: a string's only GetById-reachable own property is `length`; its prototype is always `runtime.stringPrototype` (`PinnedValue<JSString>`, RuntimeHermesValueFields.def:25), not in RuntimeOffsets yet and movable, so it needs an offsetof entry rather than an embedded pointer. A guard of string tag + String.prototype class lazy ID + slot load is sound; eligibility as for own entries (no NoCache dictionary, no accessor). String.prototype has 40 properties, below the dictionary threshold.
- A direct `charCodeAt` call must also check the loaded value is that NativeFunction: replacing the property's value keeps String.prototype's class.

## Approaches

- A (proposed first): string receivers in the GetById tier as a new entry kind. Inline `length` (tag check, load, mask, convert to number) and String.prototype method entries (tag check, String.prototype class ID, slot load). Targets the ~8%.
- B (separate project): call-target specialization, calling a recorded native directly (and `charCodeAt` inline for Dynamic strings, helper for External). Targets the further ~5% and generalizes to other natives.
- C: compile-time string typing. Not viable; no type information at these sites.

Full research notes were in the session scratchpad (string-getbyid.md); the facts above are the load-bearing ones.
