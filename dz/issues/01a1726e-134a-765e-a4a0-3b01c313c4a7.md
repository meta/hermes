A chain entry whose receiver class now reaches a Rejected walk verdict
over a path that contains an unflagged object never settles: every
miss for that receiver class keeps paying for two walks plus the
forwarded lookup. Performance only; the values are correct.

Where (lib/VM/JIT/JitHandlers.cpp, as of the GetById chain entries
feature on x86-jit):

- `jitWalkChain` clears `allFlagged` when it visits a prototype whose
  class is neither flagged (`isCachedUsingEpoch`) nor typed, and when
  it stops at an excluded object.
- `chainFastRefresh` walks whenever `hasChainCandidate` holds (a live
  chain entry for the receiver class with a stale epoch and
  `refreshFailedAt != now`), and gives up on anything but Found with
  `allFlagged`.
- `chainAfterForward` sets `refreshFailedAt = now` on a different
  verdict only if `w.allFlagged`, because a verdict that depends on an
  unflagged object can change without an epoch bump
  (test/jit/getbyid-chain-refresh-settle.js pins this). So with an
  unflagged object on the path the entry stays a candidate.
- `_jit_get_by_id` runs `chainAfterForward` after forwarding when
  nothing was harvested; `_jit_get_by_id_refresh` runs it whenever a
  candidate exists.

Result: for a Rejected verdict over an unflagged path (for example an
unflagged replacement prototype that lacks the property, or a chain
that now ends before reaching it), each miss does the fast-refresh
walk, the forwarded lookup and the post-forward walk, until the next
epoch bump, after which the same happens again. A walk that stops at an
excluded object (a dictionary, which deleting a property also produces;
a lazy, host or proxy object) is not settled by the candidate fix
below.

Candidate fix: when the verdict is Rejected and the walk stopped at
the end of the chain (null parent) or at the depth limit -- not at an
excluded object, which flagging cannot describe -- flag the visited
path (`flagChainPath` over the levels walked), and, if the epoch did
not move while flagging, set `refreshFailedAt = now`. The verdict then
depends only on flagged objects, so suppressing until the next bump is
sound. getbyid-chain-refresh-settle.js would need re-deriving: its
`empty` would become flagged, so `empty.p = 9` would bump the epoch.

Found by the final review of the GetById chain entries feature; see
the "Known limitations" note in
doc/superpowers/specs/2026-10-24-jit-getbyid-chain-design.md.
