From the external review REVIEW-jit-recompilation.md (2026-09-06),
finding 1 (P2); reproduced on the current tip.

considerRecompile() (lib/VM/JIT/JitCompiler.cpp, warm-scan) treats ANY
non-null property-cache entry as proof that recompilation can make
progress. That includes caches that were already warm and specialized in
the current body. The spec mandated exactly this check ("at least one
property-cache entry now names a class"), so this is a spec defect
faithfully implemented.

Consequence: a site that declines forever (e.g. an accessor write, which
never populates the write cache) drives the decline counter while an
unrelated warm cache satisfies the progress check; the default budget of
one is spent on a byte-identical body before a later phase warms the
cache that actually matters, and that site then stays helper-only for
the function's lifetime. Larger budgets compile identical bodies
repeatedly.

Reproducer (verified: version 2 installed before "late phase", same two
cold sites, o.q never gets its tier):

    function f(o, late) {
      o.s = 1;
      if (late) o.q = 2;
      return o.p;
    }
    var o = {p: 0, q: 0, set s(v) {}};
    for (var i = 0; i < 200; ++i) f(o, false);
    print('late phase');
    for (var i = 0; i < 200; ++i) f(o, true);
    print(o.q);

    hermes -fno-inline -Xjit -Xjit-threshold=4 -Xdump-jitcode=2 t.js

Fix direction: the emitter records WHICH cache indices were cold
(per-kind index lists in JitFunctionData, replacing the bare
coldByIdSites count as the progress source); considerRecompile requires
one of those specific entries to have warmed. Regression: the phased
reproducer must keep its budget through phase one and install a PutById
specialization for o.q after the branch warms.
