Running benchmarks/octane/mandreel.js (from the main-tree benchmark
corpus; Octane's Mandreel-compiled C++ workload) on a Release/clang
x86-64 build, Hermes peaks at ~547 MB RSS where V8 (node 24) uses
~92 MB and JSC (trunk jsvu build) ~128 MB, both in their jitless AND
baseline-JIT configurations. mandreel_latency.js shows the same.

Measured 2026-08-26 with /usr/bin/time -f rss=%MKB, single runs:

    hermes HV64 interp: 547,256 KB   (score 1711, t=8.6s)
    hermes HV32 interp: 547,256 KB   (score 1629)
    hermes HV64 -Xjit:  546,868 KB
    hermes HV32 -Xjit:  546,996 KB
    node --jitless:      92,172 KB
    jsc  --useJIT=false:127,620 KB

Two properties narrow the cause:
1. The number is invariant across HV64/HV32 (value/pointer width) and
   interpreter/JIT, to within ~0.1%. Whatever it is, it is not scaled
   by HermesValue width and not JIT metadata.
2. No other Octane benchmark shows it (next-largest Hermes RSS in the
   same sweep: splay at ~240 MB HV64 / ~134 MB HV32, which HV32 halves
   as expected; typescript ~140 MB).

Not yet investigated: whether the memory is GC heap vs malloc
(compiler/parser/bytecode side), whether it is a peak or a plateau,
and what allocation produces it. Suspicion to check first: mandreel.js
is a large (multi-MB) source with Emscripten-style flat-memory code;
compile-time structures or a pathologically retained allocation could
both produce a mode-invariant number.

Found during a cross-engine benchmark sweep on the x86-jit branch.
(Originally filed as component "vm" titled as a VM RSS anomaly; the
investigation below localized it to the compiler, and the issue was
retitled and moved to component "compiler" accordingly — see the log.)

    Investigated 2026-08-26 (Release/clang x86-64, same binary as the report).
    Root cause localized: this is COMPILER memory, not VM/GC, and it is a
    large LINEAR per-statement footprint, not a leak or a superlinear blowup.
    
    Evidence chain:
    
    1. Compile/run split: `-emit-binary` on mandreel.js alone peaks at
       547 MB; running the resulting 12 MB .hbc peaks at 52 MB (and scores
       the same). Explains the HV-mode/JIT invariance: those affect only
       the runtime.
    2. Not the optimizer: -O0 compiles at 532 MB, -Og 531 MB, -O 547 MB.
    3. Stage ladder on mandreel (-O0): parse+sema 109 MB; through IRGen
       (-dump-ir) 290 MB; through RA (-dump-lra) 566 MB. RA is also 3.8 s
       of the ~4 s compile.
    4. Shape: mandreel.js has one function spanning ~2.77 MB of the 5 MB
       file (Mandreel whole-program output), and unlike every other Octane
       file it is ~100% dense executable code. typescript.js (2.5 MB, mostly
       string literals) compiles in 59 MB.
    5. Synthetics (straight-line function of `var xN = xN-1 + N|0;`
       statements, -O0): 60k statements → 223 MB, 120k → 437 MB — linear,
       ~3.6 KB of peak RSS per simple statement (sema ~1 KB, IR ~+1.3 KB,
       RA ~+1.7 KB). A branchy variant (6k extra basic blocks) is no worse
       (200 MB), so no BBs-x-regs quadratic term at -O0. Many-small-functions
       at the same total statement count: 140 MB — the giant function costs
       ~1.6x more per statement, but the dominant factor is simply
       statements x per-statement cost with AST + sema tables + IR (+ RA
       structures) all live at once.
    6. `-lazy` does not rescue this shape: 406 MB peak and the score halves
       (931 vs 1711) because the giant function is the benchmark itself.
    
    Ballpark check: mandreel ≈ 190k statements x ~3.6 KB ≈ 600 MB-ish,
    consistent with the observed 547-566 MB.
    
    Severity framing: devices running precompiled HBC never pay this; it
    lands on eager in-process compilation of dense multi-MB sources — the
    CLI direct-exec path (hence the benchmark numbers), build-time
    compilation on CI machines, and any embedder eval() of large bundles.
    
    Directions worth considering (not attempted): compile-and-release per
    function instead of keeping the whole program's AST+IR live
    simultaneously; shrinking per-instruction IR footprint; freeing the AST
    before BCGen. No profiler on this host (no valgrind/heaptrack), so the
    per-structure attribution within each stage is unmeasured; the stage
    ladder above is external RSS.
