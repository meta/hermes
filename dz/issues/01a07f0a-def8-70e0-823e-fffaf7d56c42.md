The inline PutByVal fast-array tier (emitPutByValFastArrayTier) guards
on CellKind::JSArrayKind exactly, so every typed-array store declines
to _sh_ljs_put_by_val_rjs: a C++ call with handle setup, virtual
haveOwnIndexed + setOwnIndexed dispatch, and a GCScopeMarkerRAII per
element.

Measured 2026-09-08, Release/clang x86-64 (cmake-build-x86jit-rel),
precompiled bytecode, identical fill loops (1000 elements x 20000
iterations, Int32Array vs dense Array):

    arr-store interp: ~227 ms   JIT: ~81 ms   (2.8x from inline tier)
    ta-store  interp: ~246 ms   JIT: ~240 ms  (~3%; helper-bound)

perf on the JIT ta-store run: putByValWithReceiver_RJS 41.5%,
JSTypedArrayBase::polyWriteNoAlloc 14.6%, _setOwnIndexedImpl 9.0%,
_haveOwnIndexedImpl 2.7% -- ~70% of the run is the per-store helper.

The inline sequence for e.g. Int32Array is short: kind check (or kind
range for a shared tier), attached + bounds check against length,
key double->uint32 as in the fast-array tier, value double->element
conversion (cvttsd2si for integer kinds, a truncating store for
float kinds; JS semantics for out-of-range int32 conversion need the
same care the static compiler's typed-array paths take), then a raw
store into the data block -- no write barrier, since typed-array
storage holds no GC pointers.

Element-kind specialization (emit only the tier for the kind actually
observed at the site) is the planned first consumer of per-version
feedback records (JitVersionData::consumerRecords), though an
unspecialized kind-dispatching tier already removes the helper call.
