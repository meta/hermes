`obj[key]` with a string key has no cache: every get, put and
`hasOwnProperty.call(obj, key)` does a full hidden-class lookup. A
runtime-wide cache keyed on (hidden class, symbol) makes pixel-grid-small
16.5% faster under HV64 and 17.7% under HV32 in a throwaway prototype.
Nothing is committed; this records the measurement and the design the
prototype used.

## Where the time goes

Almost all of it is the prop-copy loop of React's `jsxProd`:

```js
for (propName in config) {
  if (hasOwnProperty.call(config, propName) &&
      propName !== 'key' && propName !== 'ref')
    props[propName] = config[propName];
}
```

Share of run time (perf, HV64, x86-jit at eeacdf640):

| benchmark        | put  | hasOwnProperty | get  | total |
|------------------|------|----------------|------|-------|
| pixel-grid-small | 9.9% | 5.3%           | 4.2% | 19.4% |
| draw             | 2.4% | 1.8%           | 3.5% | 7.7%  |
| relay-feed       | 1.4% | 0.1%           | 1.6% | ~3%   |

Three facts shape the design:

- The keys are already uniqued. `for-in` produces its keys from symbols,
  so `StringPrimitive::isUniqued()` holds and the string carries its
  SymbolID; hashing and identifier lookup are 0.0% of the profile. No
  compiler support is needed to pass the symbol.
- The sites are megamorphic in the key: one site sees every prop name.
  A one-entry cache at the site would miss; a table keyed on
  (class, symbol) hits.
- The store adds a property, so it needs the add cache's validation
  (start class, result class, parent epoch), not a slot write.

## Prototype

`GetByVal` and `PutByVal*` have no cache operand, so the tables live in
the Runtime and the bytecode is unchanged. All fast paths are C++, behind
the call JIT code already makes; nothing is emitted inline.

- Read table, 1024 entries, direct-mapped on a hash of (class, symbol):
  class (weak root), symbol, slot, writable bit. Filled only for an own,
  non-accessor property of a class that is not a dictionary, host object,
  proxy, lazy object or indexed storage.
- Add table, 1024 entries: start class and result class (weak roots),
  symbol, slot, parent epoch. Filled only when the result class is a
  plain add transition from the start class with default flags and no
  parent has the name as an accessor or read-only; the parents are marked
  with `setCachedUsingEpoch`, as `tryCacheAddProperty` does.
- Get: in `_sh_ljs_get_by_val_with_receiver_rjs`, after the numeric
  path. Uniqued string key, read-table hit, load the slot.
- hasOwnProperty: at the top of `objectPrototypeHasOwnProperty`. A
  read-table hit returns true.
- Put: in `putByValWithReceiver_RJS`. A writable read-table hit stores
  the slot; an add-table hit with a matching epoch calls
  `addNewOwnPropertyInSlot`.
- The weak class roots are marked in `Runtime::markWeakRoots`. A live
  class keeps its symbols alive, so the tables hold the symbol as a bare
  id.

## Measurement

2026-11-11, x86-64 Release, `HERMESVM_ALLOW_JIT=2`, `-Xjit`, bytecode
from each build's `hermesc -O`, `taskset -c 2`, configurations
alternated, medians of 7 runs (3 for full-size pixel-grid). "off" is the
patched binary with every fast path disabled; it is within 1% of the
unpatched tip everywhere. Ratios are against "off".

| benchmark        | mode | tip    | off    | get    | +has   | +put   | ratio |
|------------------|------|--------|--------|--------|--------|--------|-------|
| pixel-grid-small | HV64 | 191162 | 193110 | 199900 | 206753 | 224986 | 1.165 |
| pixel-grid-small | HV32 | 212040 | 211253 | 219042 | 227429 | 248595 | 1.177 |
| pixel-grid       | HV64 | 12439  | 12522  |        |        | 13501  | 1.078 |
| pixel-grid       | HV32 | 13121  | 13088  |        |        | 14546  | 1.111 |
| draw             | HV64 | 41042  | 40893  | 41497  | 42041  | 43008  | 1.052 |
| draw             | HV32 | 38051  | 37922  | 38574  | 39111  | 39455  | 1.040 |
| relay-feed       | HV64 | 3584   | 3584   | 3584   | 3571   | 3584   | 1.000 |
| relay-feed       | HV32 | 4149   | 4149   | 4184   | 4132   | 4184   | 1.008 |

That recovers about three quarters of the 19.4% on pixel-grid-small and
about two thirds of the 7.7% on draw. relay-feed does not move.

Table activity with all three paths on (HV64):

| benchmark        | get hit / miss  | has hit / fill   | put add hit / fill | put miss |
|------------------|-----------------|------------------|--------------------|----------|
| pixel-grid-small | 5216734 / 29638 | 5111106 / 24986  | 5136834 / 60       | 0        |
| draw             | 920073 / 51490  | 508992 / 11911   | 283315 / 48        | 0        |
| relay-feed       | 135161 / 18462  | 4248 / 140       | 22787 / 157        | 714      |

A "fill" is a miss that entered the table; a "miss" could not be cached.
1024 entries are enough for these benchmarks, and the parent epoch does
not churn: the add table refills 60 times in 5.1 million stores.

`check-hermes` on the prototype, Release, HV64 and HV32: no unexpected
failures.

## What is left per operation

perf at 4000 Hz with call chains and jitdump, HV64, pixel-grid-small,
two runs per configuration, the same patched binary with the paths off
and on. Samples are those under the three sites in `jsxProd`; each run
executes about 5.1 million of each operation.

| operation      | off: samples | on: samples | off: ns/op | on: ns/op |
|----------------|--------------|-------------|------------|-----------|
| put            | 1585         | 401         | 38         | 10        |
| hasOwnProperty | 1019         | 346         | 25         | 8         |
| get            | 633          | 136         | 15         | 3         |
| total          | 3237 (18.9%) | 883 (5.8%)  |            |           |

Where the 883 remaining samples are:

- put, 401: 128 in `addNewOwnPropertyInSlot`, the add itself. About 75
  at the two table compares: the put probes the read table, misses, and
  then probes the add table. The rest is entry, exit, encoding the value
  and barriers.
- hasOwnProperty, 346: the probe is about 35. The rest is the native
  call: the `Call2` sequence in JIT code, `NativeFunction::_jitCallImpl`
  and the function's entry. `objectPrototypeHasOwnProperty` has 198 self
  samples with the path off and 198 with it on.
- get, 136: the probe is about 30; the rest is the call and the numeric
  check that precedes it.

An inline probe in JIT code can at most remove what is not the add or
the probe: about 630 samples, 4% of pixel-grid-small. Half of that is
`hasOwnProperty`, which needs the JIT to recognize the callee, not an
inline table probe. On draw the three sites are 0.7% of the run after the
patch, so nothing is left to gain there. The first step is 16.5%; the
inline probe is a later, separate item.

Two cheaper things the profile shows:

- A put should probe once, not twice.
- `GetNextPName` is unchanged at 303 samples (2.0%) in `jsxProd`,
  now as large as each of the three operations.

## Not done

- No ASan or Debug build of the prototype; assertions were off. Its GC
  safety was checked only by reading.
- The interpreter's `GetByVal` and `PutByVal` do not go through the
  patched functions, so only JIT and natively compiled code benefit.
- arm64 was not built.

## To settle in a design

- Where the fast paths belong so that the interpreter, the JIT and
  native code share them.
- Table size, placement and replacement policy; the prototype's 1024
  direct-mapped entries were not tuned.
- Whether `hasOwnProperty` gets a path that skips the native call.
- `in`, `delete` and a negative result for `hasOwnProperty` are not
  covered; these benchmarks do not need them (14 negative lookups on
  pixel-grid-small).
