test/jit/x86-64/counters-slow-call-kinds.js fails on a Handle-San build
(cmake-build-hs-hv32: HEAP_HV_PREFER32 + HERMESVM_SANITIZE_HANDLES). It
passes in every other configuration.

Cause: the test pipes 2>&1 into FileCheck, and a Handle-San runtime prints
a four-line banner before any program output:

    Warning: you are using handle sanitization with random sampling.
    Sanitize Rate: 1.00%
    Sanitize Rate Seed: 1878560782
    Re-run with -gc-sanitize-handles-random-seed=... for deterministic crashes.

The test's first directive is a bare `CHECK: 2`, which matches inside that
banner instead of the program's own output, so the following CHECK-NEXT
chain derails:

    counters-slow-call-kinds.js:29:16: error: CHECK-NEXT: is on the same
      line as previous match
    // CHECK-NEXT: 3
    <stdin>:3:28: note: 'next' match was here
    Sanitize Rate Seed: 1932720373

The same command on cmake-build-x86jit-hv32 prints `2 / 3 / 4 / JIT
counters:` with no banner and passes.

Not a regression: the test landed in 04612724f, three commits before the
inline-write-barrier series, and concerns -Xjit-emit-counters, which that
series does not touch.

Fix is a choice, deliberately left open: make the CHECKs banner-tolerant
(anchor them, e.g. CHECK-LABEL or a more specific pattern), or mark the
file UNSUPPORTED: handle_san the way the two -emitted pin tests are. The
first keeps coverage on that config and is probably right, since nothing
about the counters is mode-specific.
