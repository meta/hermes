Discovered while verifying Task 4 of the imul-instruction plan (JIT:
implement Imul on both backends). It looked at first like a runtime
bug in the arm64 build; it is actually a stale build-tree trap in the
`IMPORT_HOST_COMPILERS` cross-build setup. Root-caused and fixed
2026-09-10; recorded here so the trap and its symptom are searchable
next time it bites someone.

## The trap

`cmake-build-arm64` is configured with `-DIMPORT_HOST_COMPILERS=
$PWD/cmake-build-host/ImportHostCompilers.cmake` (see
`doc/JITTesting.md`): it reuses `hermesc`/`shermes` built for the host
(x86-64) out of `cmake-build-host`, rather than rebuilding them for
the cross target. One of the things a host `hermesc` build produces is
the compiled `InternalBytecode` blob (`lib/InternalJavaScript/`) that
gets linked into every `hermes`/`hermesc` binary, arm64 included.

This plan's Task 2 ("IR: add ImulInst" / "HBC: add the Imul opcode")
inserted a new opcode into the bytecode format and renumbered its
neighbors. `cmake-build-host` was last built *before* that change
(2026-09-07); `cmake-build-arm64` was rebuilt *after* it, against the
current source, but `IMPORT_HOST_COMPILERS` meant it kept re-linking
against the OLD `cmake-build-host` binaries -- so the arm64 `hermes`
binary embedded an `InternalBytecode` blob compiled with the old,
pre-renumbering opcode assignments, wrapped in code that otherwise
matched the new format everywhere else.

## The misleading symptom

`Runtime` construction validates that embedded internal bytecode
before running anything, so *every* arm64 binary aborted on *every*
script, with no JIT flags involved and no user code executed yet:

    $ qemu-aarch64-static -L /usr/aarch64-linux-gnu bin/hermes /tmp/t.js
    # /tmp/t.js: var x = 1 + 2; print(x);
    hermes: .../lib/VM/CodeBlock.cpp:75: auto hermes::vm::validateInstructions(ArrayRef<uint8_t>, unsigned int)::(anonymous class)::operator()(OperandAddr32, OperandReg8) const: Assertion `reg8 < frameSize && "invalid register index"' failed.
    qemu: uncaught target signal 6 (Aborted) - core dumped

This looked exactly like a genuine cross-arch runtime bug, and two
things especially reinforced that reading during the original
investigation: (1) it reproduced identically whether or not the Imul
JIT-emitter diff was applied (true, but for the wrong reason -- the
diff never touched the opcode numbering, so it could not have caused
or fixed this either way), and (2) loading a `.hbc` compiled by an
up-to-date, known-good NATIVE x86_64 `hermesc` directly into the arm64
binary crashed the same way -- which felt like it ruled out a
bytecode-format mismatch, but actually didn't: the assert fires while
validating the *embedded* `InternalBytecode` during `Runtime`
construction, before the user's own `.hbc` is ever read, so a
known-good user script or `.hbc` was never going to change the
outcome.

This also explains the collateral damage: the external
`check-napi-node-tests` custom target failed the same way (any hermes
invocation aborts at startup), which made `check-hermes` abort before
reaching its lit run, and the full `LIT_FILTER='jit/'` arm64 suite
failed all 53 `test/jit/*.js` tests with the identical assertion.

## Remedy

Rebuild the imported host-compiler tree whenever the bytecode format
changes, before rebuilding a tree that imports it:

    cmake --build cmake-build-host --target hermesc shermes
    cmake --build cmake-build-arm64 --target hermes

After that, the smoke script prints `3` and the full arm64 jit suite
is green: 53 expected passes, 50 unsupported, 0 failures (same
`LIT_FILTER='jit/'` invocation as before). Nothing in the VM, the
bytecode reader, or the JIT emitters needed to change -- the code was
correct throughout; only the stale `cmake-build-host` artifacts were
wrong.

Generalizing: any tree built with `IMPORT_HOST_COMPILERS` silently
goes stale across a bytecode-format change (new/renumbered opcodes,
changed instruction encoding, changed `InternalBytecode` content) if
the imported host tree isn't rebuilt first, and the failure mode is
this same misleading `reg8 < frameSize` (or similar) assertion at
`Runtime` construction, indistinguishable at first glance from a real
cross-arch bug. Worth checking `cmake-build-host`'s build timestamp
first, before investigating a "the arm64/qemu runtime is broken"
theory.
